# 流式取消与正文提交

## 背景与范围

小说生成、修复及 Creative
Hub 的 HTTP 请求会在请求体传完后继续输出很久。请求体生命周期、模型生命周期与正文提交必须分别处理，否则正常 POST 会误取消，或断开后继续等待模型并保存部分正文。

## 当前规则

- HTTP 客户端取消以 `res.close` 和 `req.aborted` 为依据；`req.close`
  仅表示请求读取结束。正常响应结束不算取消。
- 章节生成与修复通过 `runClientSSE`
  在模型准备前绑定信号，作用域持续到最终保存完成。后台自动导演沿用持久任务自己的执行信号。
- PromptRunner 合并显式信号与当前执行信号；结构化调用、JSON 修复和语义重试在取消后必须立即上抛，不能切换模型掩盖取消。
- `guardStreamStall`
  同时等待下一分片、取消和超时。超时后中止底层请求，异步清理只做尽力处理，不能等待挂起的生成器
  `return()`。
- 流完成 Promise 拒绝时不能用已显示的分片正文兜底落库。所有生成及修复的正文提交还需独立执行原稿版本校验和替换前备份。
- 取消信号只保证本进程及时停止；跨实例并发以
  [持久化围栏](execution-cancellation-and-fencing.md) 为最终约束。

## 诊断路径

流长期显示生成中时，先确认是在模型连接建立、下一分片读取还是完成后的审校阶段；停滞计时不能把消费者处理耗时计入 provider 超时。超时已抛出但调用仍未返回时，检查清理是否等待未完成的
`next()`。

正文意外替换时，检查 `expectedContent`
是否来自生成开始时的正文、写入是否原子匹配、是否有人捕获流完成异常并改用部分输出。
