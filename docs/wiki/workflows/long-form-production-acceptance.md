# 长篇生产成熟度验收

## 目标

“支持写长篇”不能只由单元测试数量证明。系统必须在固定输入、可记录模型响应和可重复运行的条件下，证明能够持续推进章节、处理中断、避免重复写入，并在长线记忆出现压力时给出可解释的恢复或质量债务。

## 10 分验收维度

| 维度 | 验收要求 |
| --- | --- |
| 完整生产链 | 从创意、方向、书级规划、分卷、拆章、章节写作、审校、修复到导出均有明确状态和恢复入口 |
| 连续推进 | 固定样本至少覆盖 100 章，按批次推进后章节数量、顺序和状态正确，不能因局部质量债务停止整本书 |
| 幂等性 | 重复点击继续、重复消费命令、重复恢复同一批次不会重复生成、覆盖已保护正文或创建重复账本记录 |
| 崩溃恢复 | API/Worker 在章节批次任意阶段退出后，重启能识别真实进度，从最近安全产物继续；已完成章节不重复写入 |
| 全书一致性 | 世界规则、角色状态、事实、时间线、开放伏笔和卷间摘要在长线运行中可追踪，冲突能变成质量债务或重规划信号 |
| 上下文预算 | 每轮上下文有明确保留、压缩和丢弃记录；长篇运行不会因历史线性增长而失控 |
| AI 决策边界 | 意图、风险、重规划和上下文取舍以结构化 AI 结果为主，确定性代码只做安全校验和结果落库 |
| 用户可恢复 | 新手能看到当前进度、暂停原因、影响范围和下一步；恢复、跳过和重规划不会要求用户理解内部状态字段 |
| 成本与延迟 | 记录每章和每阶段 token、重试、耗时和失败率；超预算时能暂停或建议调整模型，而不是静默等待 |
| 发布可靠性 | shared/server/client 可构建，数据库双 schema 对齐，测试和部署健康检查可重复通过 |

## 固定验收样本

验收样本应固定书籍设定、角色、卷结构、模型响应或录制回放，并至少覆盖：

- 100 章以上、至少 4 卷的完整项目；
- 第 1、30、60、100 章的阶段性事实和伏笔检查；
- 章节批次中途 Worker 退出、API 重启、重复继续和重复恢复；
- 局部质量债务、章节修复失败、全书重规划、受保护正文和数据完整性错误；
- 用户在中途编辑角色或世界规则后，后续章节能读取变更影响；
- 最终导出与数据库章节顺序、正文和状态一致。

## 判定规则

单元测试通过只说明局部合同成立，不等于长篇验收通过。只有固定样本能够在不依赖临时人工改数据库的情况下完成上述流程，并保留运行记录、checkpoint、账本和成本证据，才可以宣称达到超长篇生产标准。

局部章节质量问题必须保持为可见质量债务，不得直接升级成全局停止。只有明确重规划、无可用正文、受保护内容风险、运行安全风险或数据完整性风险才允许阻断全书自动推进。

## 固定验收实现边界

固定样本使用独立临时 SQLite 和录制式模型响应，通过真实章节运行时完成正文保存，再由验收 fixture 写入并校验摘要、事实、状态快照、上下文预算证据与伏笔账本。章节流水线的调度器仍保持异步，因此确定性验收直接调用生产执行器；Worker 进程级 SIGKILL 恢复由 `directorWorkerProcessRecoveryRealPrisma.test.js` 单独证明，不能把两者混写成同一项证据。

验收必须区分三类状态：章节可用但存在局部质量债务时继续整书；明确重规划、无可用正文、受保护正文风险或数据完整性错误时才阻断；Worker 命令只有在真实继续任务 Promise 完成后才能标记成功。stale lease 回收必须把扫描时的状态、owner 和过期时间作为条件更新，CAS 未命中时不得覆盖新 Worker 的任务状态。

刷新恢复以数据库活动流水线为事实源。编辑页首次进入时查询当前小说的活动任务并恢复 job ID，随后复用既有轮询；启动失败必须显示下一步反馈，不能只留下等待中的空界面。

## 验收记录

当前固定样本已通过：100 章、4 卷、GenerationJob 100/100 成功、100 条摘要、100 条状态快照、100 条事实、100 条上下文预算记录；第 30/60 章重放后章节仍唯一，伏笔从第 1 章建立并在第 100 章回收，任务 token 与调用次数均有持久化记录。该记录证明可重复的长篇状态与恢复不变量，不代表真实模型质量已被固定 fixture 代替。

## 创建事务与幂等

新手创建项目由稳定的 `creationRequestId` 驱动。服务端先恢复同一请求对应的 workflow task，再复用稳定小说 ID 或创建小说，最后完成 task 绑定。网络中断后的重试必须返回同一小说和 task；不能依赖前端同时成功完成多个独立请求，也不能通过删除孤立记录来恢复。

章节正文落盘支持 execution fence：调用方携带 `executionId` 与 `checkpointVersion` 时，保存前后都必须确认 execution 仍为 running、租约未过期且版本未变化；旧执行失去租约后不得覆盖新执行的正文或产物。未携带 execution context 的兼容入口保持原有行为，新的导演执行链应优先传递 fence，逐步收紧到所有可重试写入。

## 失败模式与诊断

恢复样本审计通过 `server/scripts/director-recovery-sample-audit.cjs` 读取已构建的导演恢复审计模块。该脚本必须跟随 `server/src/services/novel/director/recovery/` 的模块边界；如果构建后仍引用旧的平铺路径，审计会在任何样本分析前失败。审计输出中的 `untrackedDraftChapters` 是历史数据完整性信号，不应通过删除正文或重置数据库消除，应先保留报告并补齐对应的 artifact baseline。

历史正文 baseline 使用 `server/scripts/director-chapter-draft-baseline-backfill.cjs`。命令默认只读预检，可通过 `DIRECTOR_BASELINE_NOVEL_ID` 和 `DIRECTOR_BASELINE_TAKE` 限定范围；只有明确设置 `DIRECTOR_BASELINE_WRITE=1` 才写入。写入操作只为正文非空且缺少 baseline 的章节创建 `backfilled` artifact，遇到唯一冲突则跳过，不覆盖章节正文，不删除任何数据。执行写入前仍需完成数据库备份和备份可读性检查。
