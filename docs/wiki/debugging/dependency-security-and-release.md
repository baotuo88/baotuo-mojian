# 依赖安全检查与发布判断

## 背景

GitHub job 显示成功，不代表其中的依赖审计没有漏洞。配置了 `continue-on-error`
的步骤即使退出失败，整个任务也可能保持绿色。发布检查必须读取 audit 报告和失败步骤，不能只读取 workflow 的最终颜色。

## 当前规则

- 生产依赖审计使用
  `pnpm audit --prod --audit-level=moderate`，失败必须阻止发布。
- 全量依赖审计仍报告开发和构建工具告警。上游没有补丁时，必须逐项记录受影响包、公告、输入来源和实际运行位置，不能把报告失败描述为“没有漏洞”。
- 优先在兼容版本范围内升级，核对锁文件差异。必须跨主版本时，确认项目实际使用的API、上游迁移说明和验证范围，不能只覆盖某个内部包来混用不兼容版本。
- 修补依赖后复查生产与全量报告，并运行受影响的类型检查、测试和部署构建。
- 不以忽略所有无补丁漏洞、降低报告严重等级或整体允许失败来代替生产依赖修补。

## 构建工具与部署产物

`braces` 的
[GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
影响构建期模式解析。当前依赖来自客户端 Tailwind
CSS 和页面构建插件；Tailwind 扫描模式由仓库配置提供，不接收小说正文、短剧台本、用户上传文件名或 HTTP 参数作为模式。上游暂无修复版本时保留全量审计告警，不能伪造补丁版本。

Web 部署产物是 Nginx 和静态资源，不运行这些构建工具。API 镜像的依赖安装仍包含工作区开发依赖，因此包文件可能存在于镜像中；“没有产品调用路径”和“镜像不含该包”是不同结论。`--prod`
审计也不是容器系统包或全部文件的漏洞扫描。

如果未来增加运行时 glob、允许用户输入构建模式、动态启用相关插件，必须重新评估这项边界，不能沿用不可达结论。上游提供修复后应升级并移除对应债务说明。

## 验证边界

依赖审计只能识别公告数据库中的已知问题。TypeScript 和服务测试不能代替浏览器中复杂富文本行为的验收；按照项目规则，界面交互验收由用户执行。
